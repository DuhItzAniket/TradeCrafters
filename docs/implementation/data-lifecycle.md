# Data lifecycle and small-demo operations

This is the operating policy for the hosted **synthetic portfolio demo**, maintained by Aniket Kumar and Annapurna S. It does not enable real funds, real brokerage accounts or licensed real-time feeds. M3 student research remains deferred. Review this policy when registration volume, hosting or data providers change.

## Registration and access

The public demo accepts GitHub OAuth registration. Production password registration and account linking are disabled. A verified provider identity owns its application account; an email/name supplied by a browser cannot establish ownership. GitHub can be unavailable or deny authorization: retain existing receipts and retry provider sign-in later, without enabling a password bypass. Admin status requires an explicit reviewed operator grant, an enrolled verified authenticator and a fresh session proof.

One active simulation account is allowed per identity, with a fixed opening grant and archived resets. Request/body/list limits, persistent per-network/global admission and the twelve-connection runtime ceiling bound bursts. These are **not a lifetime registration/storage quota**. Review Aiven storage weekly and before inviting a class. At 70% storage, stop invitations and investigate growth; at 85% or repeated capacity failures, pause funding/execution, restrict new access operationally and recover capacity before reopening. Do not silently raise connection caps or add paid capacity.

## Retention

| Data                                                                        | Live policy                                                                                                                                                                                                                                                    |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GitHub identity/profile and encrypted enrolled factors                      | Retained while the account exists. Provider credentials are private server data; never exported into browser logs or issues.                                                                                                                                   |
| Sessions and OAuth/verification/trusted-device records                      | Application expiry is checked on access. A MySQL event removes records more than one hour past expiry, in batches of at most 1,000 per table/minute. Deleting an expired session also removes its step-up proof.                                               |
| Step-up proofs and used authenticator-code digests                          | Proofs expire after five minutes, code digests after 90 seconds; the same event removes rows more than an hour past expiry. This does not change factor enrollment or recovery codes.                                                                          |
| Identity mutation/MFA attempt counters                                      | Removed after ten idle minute windows, in batches of 1,000. Active-window counters survive.                                                                                                                                                                    |
| Anonymous ingress/auth counters                                             | Existing separate minute events retain only recent windows; see [request admission](request-admission.md).                                                                                                                                                     |
| Virtual journals, receipts, positions, archived accounts and security audit | Retained for account history and reconciliation until a verified deletion request is completed. Do not prune idempotency receipts or recovery case keys independently: retrying an old case must never reset a newly enrolled factor.                          |
| Runtime diagnostics                                                         | Fixed scope (`read`, `write`, `auth`), status and duration only. No raw URL/query, identity, IP, body, token, SQL or provider response is logged by application diagnostics. Vercel platform logs have their own short retention and are not an audit archive. |

Expiry is bounded maintenance, not a guaranteed maximum deletion latency: backlog, provider shutdown or scheduler failure can delay removal. An operator checks scheduler/event execution and remaining expired-row counts during the weekly review and after restoration. Live expiry/authorization remains enforced even when maintenance is late. Automatic deletion does not touch enrolled factors, users, roles, audit cases or financial history.

## Account closure and incident recovery

Account deletion is **operator assisted**. Request it privately from the project owner through the established project contact; never publish provider IDs, email addresses, holdings, cookies or identity evidence in a GitHub issue. There is no self-service erase button or promised response time in this portfolio demo. Before opening registration beyond a personal demo, establish a durable private support/contact channel.

The operator independently verifies control of the exact provider identity, reviews the exact target, takes an encrypted checkpoint and revokes its sessions/admin role first. Inventory the subject's active/archived accounts and receipts before a reviewed transaction deletes its dependent fictional records and identity. Foreign-key failures must abort the whole transaction. Do not disable foreign-key checks, match only on a display name/email, erase another user's records or delete shared venue/rule/catalog data. This document is a procedure, **not an implemented general-purpose deletion command**; a real request requires a reviewed case and scoped implementation. Preserve only a non-identifying completion record outside the account's data.

Backups cannot be selectively edited safely. A closed account may remain encrypted until the backup retention window ends. After any restore, discard restored session authority and reapply independently retained completed-deletion cases **before exposing the application**. For a compromised factor/admin identity, use the separately reviewed [owner recovery procedure](owner-recovery.md); it does not erase financial history or grant a new role.

## Backups and audit protection

Aiven Free supplies its automated disaster-recovery backup; the console on 21 October showed the scheduled backup time as **07:44 UTC**, two historical full backups in **do-sgp1**, and a disabled Fork control even after the live service moved to Bangalore. A visible backup list is not a selectable retention/PITR entitlement. See [Aiven's Free tier](https://aiven.io/docs/products/mysql/concepts/mysql-free-tier) and [backup documentation](https://aiven.io/docs/products/mysql/concepts/mysql-backups). Do not destroy the live service to test a disabled restore control.

The owner also keeps independently encrypted logical checkpoints before schema/recovery changes and **weekly while the demo is in use**. This portable backup is an operator task; no unattended laptop or GitHub secret-bearing backup scheduler is claimed. Keep the last four weekly checkpoints and the latest successful pre-release checkpoint for at most **35 days**, then remove expired copies through the owner's normal storage workflow. Retention applies to all copies. Never prune the only independently retrieved known-good archive before its replacement is tested.

The encrypted checkpoint includes the complete security audit and recovery case keys. Keep ciphertext/report off the computer/service, with the key and hosted auth secret in separate private custody. The owner confirmed separate copies and retrieval on **21 October 2026**. Runtime grants allow audit INSERT/SELECT only; they cannot rewrite history. A database operator could still alter the database, so the independently held authenticated archive is the comparison anchor; the database audit itself is not tamper-proof or a compliance archive. The [audit-anchor command](release-operations.md#audit-anchor-check) compares retained historical audit rows before a new export.

## Failure review

The GitHub Actions public smoke workflow checks liveness, two nonce-protected pages, a real DB-backed directory/chart and anonymous portfolio denial every six hours, and can run manually. It has no production secrets, writes or owner session. A failed run is visible in Actions. The owner should enable GitHub Actions failure notifications in their own GitHub notification settings; email/push delivery has not been tested and is not guaranteed. Scheduled workflows can be delayed or disabled by GitHub inactivity.

Review failures against Vercel's fixed-scope API status/duration logs and Aiven connections/storage/scheduler. Health alone is not readiness. For repeated 503, stop new mutations and inspect caps/provider state; for an uncertain mutation, recover the saved receipt before retrying. For 429, honor Retry-After. Use the [release/incident runbook](release-operations.md) for rollback and restore; code rollback cannot reverse journals or database DDL.
